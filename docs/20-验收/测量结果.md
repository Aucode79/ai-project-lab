## 基准场景（测的是什么）

`game/bench/scenes/bench_world.tscn`（由 `game/bench/gen_scene.gd` 工具脚本生成，不手写 uid）：

- **体素地面**：spike 同款生成器（台地甲板 + 电路线 + 四角信标塔），**开碰撞**；原点 13×13 机器平台是平的，全部道具落在这块平地上
- **第一关风格道具**：一块任务牌（"任务 L1：给它接第一件活"）+ 一块角色铭牌（"mini codex · 工位 01"），MeshInstance3D + Label3D 近似
- **50 个可推倒刚体方块**：10 层塔 + 5×3×2 方墙 + 传送带上 10 块（0.5 m，摩擦 0.9 / 弹性 0.05）
- **10 m 传送带**：AnimatableBody3D 平台，0.8 m/s 单向平移，靠摩擦带走方块
- **WorldEnvironment**：明亮定稿全套（AGX、SSAO 1.2、Glow 0.45、冷色距离雾、饱和度 1.30）+ 主光 2.5 投影 + 暖白补光 0.55 + 四座信标的小粒子
- **第三人称轨道相机**：透视 fov 50，绕平台慢速环绕（10 s 约 86°）

两种入口共用一套世界逻辑：`res://bench/scenes/bench_world.tscn -- --mode=<m>`（场景直跑，渲染测量用）与 `-s res://bench/bench_main.gd -- --mode=<m>`（SceneTree 脚本入口，headless 测量用），mode ∈ smoke / physics / bake / predict / render / render-pure。

两个必须知道的场景事实（第一版实测踩出来的，脚本里已固化处理）：

1. 体素碰撞按 16 m 块**异步流式生成**。方块若在碰撞就绪前放行，整摞会穿进甲板——第一版实测 16 块穿透、最远飞出 367 m。现在场景用 6 条射线探针确认甲板四块碰撞体全部就绪后才解冻方块（`bench_world.gd` 的 `wait_collisions()/arm_physics()`）。
2. 解冻瞬间接触求解会往精确堆叠的 10 层塔里注入横向抖动直接震塌。塔以**睡眠状态**保住（游戏里堆叠物的常规做法），沉降测量针对的就是这个睡眠塔。

## 数一 · 单帧渲染耗时（1920×1080 / 25 fps / 最终光影）

**方法**：两个跑法分开测"纯渲染"与"含写盘"，各 250 帧采样、前 100 帧预热剔除（等体素流式加载与 AO 稳定），垂直同步关闭使墙钟反映真实成本。

- 纯渲染：窗口全速跑，测每帧墙钟（渲染提交 + GPU 呈现 + 脚本 + 物理）
- 含写盘：Godot Movie Maker（`--write-movie` PNG 序列 + `--fixed-fps 25`），同口径测每帧墙钟；Movie Writer 按 project 的 viewport 尺寸出片，复跑脚本用临时 `override.cfg` 把出片尺寸钉在 1920×1080（**不改 project.godot**）

**原始数字**（RTX 5060 / Forward+ / MSAA 2x + FXAA）：

| 口径 | 均值 | P95 | 最大 | 单集（10400 帧） | 63 集（655,200 帧） |
|---|---|---|---|---|---|
| 纯渲染（无写盘） | **12.69 ms** | 12.58 ms | 343 ms（孤立尖刺） | 2.20 min | **2.31 h** |
| 含 PNG 写盘 | **173.69 ms** | 187.60 ms | 322.91 ms | 30.11 min | **31.61 h** |

引擎自报的分解（Movie Maker 收尾统计，354 帧）：CPU 渲染 0.94 ms/帧、GPU 渲染 1.29 ms/帧、**PNG 编码 157.49 ms/帧**——写盘占单帧墙钟约 90%，是绝对主导项。

**判定**（spec §9.2 三档：≤0.5 s 按 25 fps；0.5–1 s 记余量；>1 s 降帧补帧或并行渲染二选一）：

- 纯渲染 0.0127 s、含写盘 0.174 s，**双双落在 ≤0.5 s 档 → 按 25 fps 出片成立**，无需降帧补帧
- 但要记一条余量警告：如果未来光影升级（SDFGI/体积光）把纯渲染推高一个量级，先撞线的是写盘不是渲染
- **写盘才是产能瓶颈**：逐帧 alpha PNG 下 63 集全量渲染-落盘约 31.6 小时（单机串行），且 655,200 帧 × 约 0.75 MB/帧 ≈ **470 GB 落盘量**，必须有转码/清理策略

**复跑**：

```bash
bash tools/bench/run_bench.sh            # 含 5a 纯渲染 + 5b Movie Maker（会弹窗）
bash tools/bench/run_bench.sh --skip-render
# 单项：
tools/godot/Godot_v4.7.2-stable_win64_console.exe --path game --resolution 1920x1080 \
  res://bench/scenes/bench_world.tscn -- --mode=render-pure
# movie 项的 override.cfg 处理见 tools/bench/run_bench.sh 步骤 5b
```

## 数二 · 烘焙耗时 + 轨道体积（最小 studio.bake 原型）

**方法**：实现 spec §7.1 口径的最小烘焙：物理固定 dt（60 Hz）逐 tick 采 50 个受物理影响实体（可推方块）的平移 + 旋转，采 10 秒；按 25 fps 插值降采样成 250 帧；定点量化 + 差分编码（格式 `MSB1` v1：位置 1 mm 定点、四元数 i16 定点、逐帧差分、休眠实体单字节、每 25 帧一个关键帧）；落盘 `motion/{runId}.bin` 并**解码回读校验**。记录开始时推倒方墙，让 10 秒里包含真实的翻倒运动。

**原始数字**（10 s 段 / 50 实体 / 250 帧；本文引用 `out/bake_report.json` 最新一次，体积另附三次实测的波动范围——方墙翻倒的剧烈程度每次不同，休眠实体越少文件越大）：

| 项 | 最新一次 | 三次实测范围 |
|---|---|---|
| 烘焙开销（插值 + 编码 + 写盘，不含 10 s 模拟等待） | **27.7 ms**（7.5 + 14.1 + 1.1） | 22.9–27.7 ms |
| 单文件体积 | 131,213 B（524.9 B/帧） | 60,965–131,213 B（243.9–524.9 B/帧） |
| 单实体单帧 | 10.5 B | 4.9–10.5 B |
| 相对裸 float（1400 B/帧）压缩 | 2.7× | 2.7–5.7×（休眠实体越多压得越多） |
| 外推单集 4 分钟（6000 帧） | 3.00 MB | 1.40–3.00 MB |
| 外推单集 8 分钟（12000 帧） | 6.01 MB | 2.79–6.01 MB |
| 回读精度 | 位置最大误差 0.5 mm；旋转最大误差 0.76°（i16 四分量定点的固有精度，非 bug） | 旋转 0.69–0.76° |
| 回读校验 | PASS（含编码器自检） | 三次全 PASS |

**判定**（spec §9.2：单集轨道设体积上限，超限则减少受物理影响的实体）：

- 建议**单集轨道上限 10 MB**：覆盖最坏实测（8 分钟满运动 6.0 MB）并留约 1.7 倍余量。63 集全走烘焙也只占约 630 MB，仓库装得下
- 烘焙的时间成本 ≈ 片段时长的 2 倍（10 s 段 = 10 s 实时模拟 + 约 25 ms 开销）——改一次配置的等待主要在"重跑物理"，编码本身不构成等待；好在 v6 裁决后烘焙只是按需可选项（多机位拼接才用）

**复跑**：

```bash
bash tools/bench/run_bench.sh            # 步骤 3/5
tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path game \
  -s res://bench/bench_main.gd -- --mode=bake
# 产物：game/bench/out/bake_report.json 与 game/bench/out/motion/*.bin
```

## 数三 · 落点前推预测成本（拖拽虚影，交互侧早量的数）

**方法**：一次预测 = 把一个刚体（0.5³ 方块，同引擎同形状同质量）克隆到**独立 physics space**（`PhysicsServer3D.space_create`，自配重力 area 与地板），前推 2 秒（120 tick @60 Hz）。两种策略对帧耗时的影响用**交错基线**（无虚影 → 每帧预测 → 无虚影 → 100 ms 降频 → 无虚影）隔离世界自身清醒程度漂移的干扰。落点探针验证独立 space 确实被主循环步进（实测 26.0 m 落到 20.49 m，正常落在虚影地板上）。

**原始数字**（引用 `out/predict_report.json` 最新一次；两次完整复跑的增量都在基线漂移以内）：

| 项 | 值 |
|---|---|
| 单次克隆重置（transform + 两个速度） | **0.17–0.22 µs** |
| "每帧预测"稳态（119 条在飞）的 physics step 增量 | **< 监测器分辨率**（最新一次 −0.0002 ms/tick，基线漂移 0.0031 ms/tick） |
| "100 ms 降频"稳态（19 条在飞）的增量 | 同上（−0.0005 ms/tick，仍在分辨率以内） |
| 增量换算帧预算 | 上界约 0.01 ms / 40 ms 帧 = **0.025%** |
| 单次 2 秒前推的墙钟延迟 | **2.00 s**（引擎步进是实时的，前推跑不赢真实时间） |

**判定**：CPU 成本可忽略——**真问题是 2 秒延迟**。同引擎、同 dt 的前推必然以真实速度推进，松手前推 2 秒的虚影要 2 秒后才出结果，学员拖拽时永远看到旧预测。可行出路（按成本排序）：缩短视界（0.5 s 内的预测 0.5 s 出，仍然滞后但可用）；后台常转 + 落点插值展示；预测降频（100 ms）在 CPU 上零代价，可无条件采纳。**这条数直接否决了"每帧同步前推 2 秒"的 naïve 方案**，交互方案设计时要按"预测是异步资源"来想。

**复跑**：

```bash
bash tools/bench/run_bench.sh            # 步骤 4/5
tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path game \
  -s res://bench/bench_main.gd -- --mode=predict
```

## 数四 · 物理引擎现状（当前默认引擎）

**读数**：`game/project.godot` 未显式设置 `physics/3d/physics_engine`（取默认值 `DEFAULT`），实际运行的 PhysicsServer 类名为 `PhysicsServer3D` → **当前默认 = Godot 内置物理（GodotPhysics3D）**。project.godot 本次未做任何改动；Jolt 对照由主会话后测（复跑脚本已就位，切换只需 project 设置 `JoltPhysics3D` 后重跑 `--mode=physics` / `--mode=predict`）。

**原始数字**（50 刚体 + 体素地面碰撞 + 传送带运转，10 s @60 Hz；引用 `out/physics_report.json` 最新一次）：

| 项 | 值 |
|---|---|
| physics step（TIME_PHYSYSICS_PROCESS 监测） | 均值 **0.0025 ms** / P95 0.0156 ms / 最大 0.0156 ms |
| 监测值口径说明 | 随场景活跃度漂移（三次复跑均值 0.003–0.016 ms：方墙清醒期高、全睡眠期低）；量级结论：50 刚体的物理在帧预算里**不可见**（<0.2%） |
| 穿透（甲板区域内方块沉到甲板面以下） | **0 次**（三次复跑均为 0） |
| 掉出世界（y<0） | **0 次** |
| 堆叠沉降（10 层塔，3 s 稳定后 → 10 s） | **0.0 mm**，倾角 0.000 m（睡眠态保持） |
| 推倒（18 冲量踢方墙底部） | 推走 4 块、最远 7.3–9.4 m（三次复跑），墙部分倒下 |
| 传送带搬运（10 s） | 平均前进 **2.49 m**（三次复跑一致；带速 0.8 m/s × 10 s 理论 8 m，滑移损耗后实得约 1/3，"能带走、不卡死"成立） |

**定性记录（spec §7.1"勉强好用"口径）**：

- **能推**：冲量响应正常，被踢方块飞出 9.4 m 后正常落地休眠
- **能堆**：精确堆叠 + 睡眠 = 沉降为零；但**醒着的精确堆叠会被解冻瞬间的求解抖动震塌**（10 层塔实测自塌）——堆叠物必须允许睡眠，这是一条实现纪律，不是引擎缺陷
- **能撞**：翻倒的墙块相互碰撞、滚落正常，无穿模、无抖动异常
- **带能运**：方块随带走、滑移可见，出带后正常掉落

**判定**：默认 Godot Physics 在"推 / 堆 / 撞、不穿模不抖"的口径下**达标**，且 50 刚体规模下性能无压力。两条实现纪律随本测量固化：碰撞就绪门（放行物理前射线探针确认体素碰撞块生成完毕）与堆叠睡眠策略。Jolt 对照待主会话裁决后补测同口径数字。

**复跑**：

```bash

tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path game \
  -s res://bench/bench_main.gd -- --mode=physics
```

## 对排期的含义（63 集总产能估算）

按一集约 4–8 分钟轨道、25 fps、约 10,400 帧/集，63 集共 **655,200 帧**：

| 环节 | 单集 | 63 集全量 | 结论 |
|---|---|---|---|
| 纯渲染 | 2.2 min | **2.3 h** | 渲染本身不构成瓶颈 |
| 渲染 + 逐帧 alpha PNG 落盘 | 30.1 min | **31.6 h**（串行） | **瓶颈在写盘**：需要并行分片（按集/片段切、多实例）或把 PNG 编码挪出捕获进程（更快编码器 / ramdisk / 后台转码队列） |
| 落盘体积 | 约 7.8 GB（10400 × 0.75 MB） | **约 470 GB** | 必须配转码与清理策略，PNG 序列只是中间产物 |
| 烘焙（按需才用） | 片段时长 × 2 | 体积上限 10 MB/集 → ≤630 MB | 仓库装得下；改配置的等待 = 重跑物理的实时时长 |
| 落点预测 | — | — | CPU 免费、延迟 2 s：交互方案要按异步资源设计（缩视界 / 后台预测）， naïve 每帧前推不可行 |
| 物理 | 不可见（<0.2% 帧预算） | — | 默认引擎可用；实体规模再放大 10 倍也未见压力，风险在体素碰撞生成时序（已有就绪门方案） |

**给排期的三句话**：

1. **出片管线按"渲染快、写盘慢"设计**——产能优化预算全部投给编码与落盘侧，不要投给渲染侧。
2. **烘焙按需、不进默认路径**（v6 已裁决），体积上限 10 MB/集可直接写进制作工具的校验。
3. **虚影交互方案需要在设计阶段就接受"预测是异步的"**，这条影响交互方案文档，不只是实现细节。
