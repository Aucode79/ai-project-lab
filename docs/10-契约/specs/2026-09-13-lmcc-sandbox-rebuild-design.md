## 2. 考试事实（设计约束源）

### 2.1 两轮结构

来源：CCF《关于举办 2026 LMCC 青少年组认证的报名通知》<https://www.ccf.org.cn/Focus/2026-06-11/902666.shtml>（不在 `/root/lmcc-research/` 内，为在线核对所得）。

| | 第一轮 | 第二轮 |
|---|---|---|
| 时间 | 2026-09-05，2 小时 | 2026-10-17，3 小时 |
| 题型 | 客观题 | **编程题** |
| 考核 | 大模型基本素养与概念 | 大模型应用、训练和微调等实践技能 |
| 门槛 | — | 第一轮达线才能参加 |

报名费 1080 元，含**算力卡支持**——考场发放算力。年龄 8–18 岁。

**第二轮是编程题**，这决定了本产品必须有学员真正写代码的部分（§7 的 Python 红线即由此而来）。

### 2.2 例卷结构与五类题型

20 道单选 × 3 分 = 60 分（1–10 基础、11–15 适中、**16–20 计算**）+ 3 道材料题共 10 小题 × 4 分 = 40 分。

材料题三类：

1. 程序填空 —— 智能体工具调用 JSON 校验器（4 空）
2. 程序阅读 —— RAG 检索助手，读 PyTorch 代码填空（3 空）
3. 论文阅读 —— 当年前沿论文（例卷用的是 2026-05 的 arXiv 论文），10 段译写材料答 3 题

计算题实例：batch/epoch 更新步数、精确率召回率、INT4 量化显存估算、NDCG@5、推理服务吞吐量。

归纳出**五类题型**：概念辨析 / 计算 / 程序填空 / 程序阅读 / 论文阅读。

**题型不是节点，是节点上的标签。** 每个内容节点可带 `examType`（五值枚举，见 §5.1），表示它对应哪类题型。这样不需要新造节点类型，也不会为了凑题型而给节点挂假旋钮。

### 2.3 官方大纲是 12 章

2026-05 版大纲共 **12 章**：一 人工智能基础概念、二 大模型基础概念、三 模型架构、四 预训练技术、五 指令微调、六 人类对齐、七 解码与部署、八 提示学习、九 复杂推理、**十 智能体**、十一 模型评测、十二 模型伦理与安全。

**智能体在 2026-05 版独立成章**（2025-10 版里它并入复杂推理）。例卷的"考纲对应"标注引用一~十一，与此结构一致。

### 2.4 id 空间锚定完整大纲，不是中小学组表

官方"中小学组知识点表"（12 模块、约 27 子模块）是**砍过的子集**：模型架构仅"注意力机制 + 主流架构"，解码与部署仅"解码方法"，智能体仅"profile 设置"。

但例卷的「考纲对应」标注引用的是 **12 章完整大纲**。实测例卷的材料题标注里，至少三条在中小学组表中**不存在**：`智能体 - 智能体工具使用`、`提示学习 - 检索增强`、`解码与部署 - 解码加速算法与实践`。

如果拿中小学组表当 id 空间，共现边会大量悬空。

**决定**：

- **id 空间 = 12 章完整大纲的全部条目**（由解析生成的权威清单，见 §5.1）
- **中小学组表降级为优先级参考**，用于判断"哪些条目对 LMCC-T 更核心"，不再充当骨架
- **v1 只实现 id 空间的一个子集**，未实现的条目在清单里标 `implemented: false`，可被共现边引用

这样 §1 的"不做全大纲覆盖"仍然成立——它约束的是**实现的节点数**，不是**命名空间的大小**。

### 2.5 一个产品价值缺口

官方《中小学大模型教育提纲》建议 10 个部分、每部分 2–4 课时，合计 20–40 课时。但例卷材料题 3 要求读懂一篇前沿论文并做数据判断——这个难度不是 20–40 课时的概念课能教出来的。

**这个缺口就是本产品的价值主张。** 它在设计里的落点具体是：**带 `examType: 论文阅读` 标签的节点**，其 `fail` 条件是"读得出材料的结论但答不出数据解释题"。

v1 是否覆盖这类节点，见开放问题 2——不覆盖就要显式降级，不能默认省略。

## 3. 形态

表面是工厂与自动化（《异星工厂》《戴森球计划》的观感），呈现为可自由改造的体素世界（《我的世界》的自由度与光影）。

底下的真相：世界里的"机器"是 Agent 与工具，"传送带"是调用链，"配方"是提示词，"电力"是 token。

| 工厂里的东西 | 实际是什么 |
|---|---|
| 机器 | 一个 Agent 或一个 MCP 工具，有 schema |
| 传送带 | 调用链，数据在机器间流动 |
| 配方 | 提示词 |
| 电力 | token |
| 良品率 | 输出合法率 |
| 库存缓冲 | 上下文与记忆 |

**LLM 就是世界本身**，不是世界里的居民，因此**没有 NPC**。

### 3.1 规则从哪来

世界的规则分两层：

- **构建期**：LLM 依据学员的配置**一次性生成规则集（RuleSet）**，冻结、可版本化。规则集是学员的主要产出物之一，不是黑盒
- **运行期**：每个 tick 按冻结的规则集演化。**大多数 tick 不调模型**，只做状态转移与校验；只有规则集显式声明"此处需要模型判断"的节点才发起调用

LLM 生成的只是初稿与默认值，学员可以改，而且改得更好——这是 §4.1 第 1 条机制的落点。

**确定性链**：冻结的规则集 + 逻辑 tick + LLM 响应缓存（键含规则集版本）。判定只对状态层做。

## 4. 教学法

**面向项目的学习**，不设线性主线。

**三阶段递进**（时间轴上的教学节奏，不是空间导航）：

1. **观摹** —— LLM 自己把世界配好并跑完，学员可单步回看每一步的配置与后果
2. **接管** —— 学员改一个旋钮，看见观测结果变化
3. **手写** —— 学员从零配置并跑完全程，得分高于观摹基线

观摹同时解决"没有主线会让零基础学员迷路"：入口就是看 LLM 跑一遍全程。

**小任务** = 给你一份坏掉的配置，你修好它，对应一个或几个知识节点。
**终极项目** = 从零配齐整套，给定随机种子回放，判定目标是否达成。

### 4.1 「手写更强」必须落在机制上

"鼓励学员自己动手"不能是口号。三条成立的机制，**必须写进评分口径**：

1. **结构设计 LLM 给不了** —— 状态 schema 怎么切、规则集怎么写、校验规则写哪几条，LLM 只给通用默认值
2. **世界之外的知识** —— 学员知道关于这个世界的具体事实，LLM 不知道
3. **成本** —— 评分含 token 与延迟，手写能用更短的规则达到同等效果

## 5. 知识网

**不设主线，设计知识网。** 依据是例卷本身：每道题的"考纲对应"大量跨模块（材料题 3 第 3 问同时标注"解码与部署-解码加速"与"复杂推理-长思维链模型"）。线性课程把这些点放在相隔五六章处，考试偏偏考联系。

### 5.1 节点 schema 与 id 空间

```
id          # 全局外键，格式 c{章号}.{章内条目序号}
implemented # v1 是否实现该条目
type        # hub | card | failure | concept
stage       # show|break|explain|build|remix|prove
label       # 官方中文路径，用于显示与对账
title       # 显示标题
kind        # 精确取值：Concept Node | Mechanism Node | Skill Node
note        # 图节点一句话摘要
examType    # 可选：概念辨析|计算|程序填空|程序阅读|论文阅读
knob        # 学员可配置的字段：类型、默认值、合法范围（hub/concept 可为空）
observe     # 改了这个之后，世界里能看到什么变化
fail        # 什么情况下这个配置是错的（必须可判定）
card        # 概念摘要（正文走 /api/content，见 §5.5）
```

**id 权威清单**：`c{章号}.{章内条目序号}` 的序号不是约定，而是**从大纲解析生成的产物**，落在 `app/content/outline_index.json`（章节名 + 条目名 + 序号 + 权重）。该文件入库、可 diff、可迁移。官方重排时更新这个文件并附迁移映射，而不是让序号默认稳定。

**`title` / `kind` / `note` 是保留字段**：`game/scripts/graph_screen.gd` 与 `game/scripts/graph3d_view.gd` 依赖它们渲染，`app/content/graph.py` 的 `build_graph()` 产出它们。新增 `knob/observe/fail` 不替代这三项。`kind` 严格使用现有三个取值，不新增第四种。

**枢纽（hub）保留。** 六个 hub↔六个 stage 一一对应，`struct` 边与 `spine` 边保留为拓扑数据。

**线索（threads）保留。** 图 payload 的顶层字段，成员指向节点 id。

**六阶段归属的默认规则**（避免逐节点臆造）：

| 节点 | 默认 stage |
|---|---|
| 概念/机制类内容节点 | `explain` |
| 带 `knob` 的节点 | `build` |
| `failure` 节点 | `explain` |
| 带 `examType` 的节点 | `prove` |

允许逐节点覆盖默认值。

**硬规则**：写不出 `observe` 和 `fail` 的节点，退回 `concept` 类型，**不允许挂假旋钮**。官方中小学组表里的概念节点有 6 条：智能与人工智能定义、常见应用领域、自然语言基础、生成与理解范式、发展历程、认知推理范畴。

**副产物**：`fail` 条件本身就是一道诊断题。

### 5.2 边的词汇表

边有 `type` 与（link 类边才有的）`rel` 两个字段：

| type | rel | 含义 | 参与判环 |
|---|---|---|---|
| link | `pre` | 前置依赖（人工维护） | **是** |
| link | `app` | 应用关系（保留） | **是** |
| link | `cooc` | **共现**（从例卷「考纲对应」自动挖） | **否**（共现天然可含环） |
| link | `confuse` | 易混对比（辨析题考的边界） | 否 |
| link | `kin` | 认知关系（保留） | 否 |
| link | `ext` | 延伸关系（保留） | 否 |
| struct | — | hub → 成员 | 否 |
| spine | — | hub → hub | 否 |

**判环只跑 `pre` 与 `app`。** 共现边必须排除在 DAG 检测之外，否则必然误报。

**共现边的输入**是从 LMCC 试卷 PDF 解析出的标注数据（建议 `app/content/exam_annotations.json`）。解析器接受**一份或多份**试卷（目录或清单），不写死单份——例卷只有 31 条标注，对约 27 个节点的网来说是薄的边层，需要更多试卷补充。解析脚本与派生数据可以入库，PDF 原件不入库。

### 5.3 与现有 Capability Graph 的关系（校验策略的明确决定）

现有拓扑（6 枢纽 + 10 知识卡 + 3 Designed Failure = 19 节点、14 条语义边、4 条线索、导入期校验）是这套设计的原型，内容层整体换血。

**决定：保留结构性校验，废弃绝对数量校验。**

| 校验 | 处置 |
|---|---|
| 成员存在性与类型正确 | 保留 |
| 成员不重复 | 保留 |
| hub↔stage 一一对应 | 保留 |
| MEMBERS 覆盖全部**已实现**内容节点（不多不少） | 保留 |
| THREADS 成员存在性 | 保留 |
| `pre` + `app` 边无环（DAG 判环） | 保留，范围见 §5.2 |
| 边的端点必须存在（含 hub） | 保留 |
| 共现边端点存在于 **id 空间**（可指向 `implemented: false` 的条目） | **新增** |
| 每个 `type == card` 的节点 `observe`/`fail` 非空 | **新增** |
| **绝对常量守恒（19/14/4/13/5）** | **废弃**。改为从内容目录派生计数，断言"派生值 == 实际组装值" |

### 5.4 导航模型：网驱动，不是脊柱驱动

**主入口是世界，不是六阶段脊柱。** 学员从世界里的机器进入节点，或从知识网直接进入节点。

- 六阶段保留为 hub 与节点的 `stage` 标签，以及 `struct`/`spine` 拓扑数据，**不再是主导航**
- 三阶段递进（§4）是教学节奏，与 `stage` 标签正交

这样"不设主线"与"保留六阶段元数据"不冲突：六阶段是内容标注，不是路径。

### 5.5 内容接口的 payload 契约

图节点与内容接口是两套 payload，都要定：

- **图节点 payload**（`/api/graph`）：§5.1 的字段，`card` 只放摘要
- **内容 payload**（`/api/content`）：知识卡正文，保留现有 `in_project` 字段（`game/scripts/card_popup.gd` 读它）；失败节点保留 `symptom` / `why` / `fix` 三字段（`game/scripts/graph_screen.gd` 读它们）

§9 重建知识节点内容时，这两套 payload 的字段名不变，避免弹层空白一类的问题。

## 6. 世界层

**结构化状态 + 冻结规则集 + 逐 tick 演化**：

```
build(config)       -> RuleSet         # 构建期，可能调 LLM，产物冻结
step(state, action) -> (state', log)   # 运行期，按 RuleSet 演化
```

LLM 只管构建期与规则集声明需要它的节点，不负责记全局状态。世界开放，**判定只对状态层做**。

- **一致性约束**：学员写的校验规则，每次转移后执行，不一致则拒绝并回滚。这是"输出不合法导致产线停摆"的教学落点，也是例卷材料题 1 的世界版
- **确定性**：单一 seed 源 + 冻结规则集 + 逻辑 tick + LLM 响应缓存（键含规则集版本）
- **token 即电力**：现有 `cost_budget_tokens` 扩展为世界的主要压力

### 6.1 tick 与 LLM 的节奏冲突

工厂的乐趣是看着产线自己跑。三条缓解手段，它们本身也是教学内容：

- 构建期冻结规则集，运行期不再重新生成
- 同 seed 同输入不重复调用（响应缓存 + 重放）
- 同一 tick 内多台机器并行处理

## 7. 学员产出物与可搬运性红线

**学员写 Python**（对齐第二轮编程题的语言）。机器接口走 **MCP over stdio**。

**红线**：学员在沙盒里写下的东西必须能直接搬进考场——工具 schema、参数校验、错误恢复、控制循环，都是可搬运的 Python。引擎与运行时细节不出现在学员面前。

MCP 的价值就在于此：学员写的工具定义是真实生态的标准。例卷材料题 1 考的就是工具调用的解析与校验。

## 8. 引擎、部署与运行时

**保留 Godot 4.7 + FastAPI sidecar。重做呈现层与形态，不换引擎。**

引擎决策依据：

| 诉求 | Godot 4 | three.js |
|---|---|---|
| 高光影 | SDFGI / VoxelGI / SSAO / SSIL / 体积雾 / AgX，引擎级内置 | 无引擎级 GI，SSGI 属社区方案，需自拼后处理管线 |
| 体素世界 | 有成熟模块 `Zylann/godot_voxel` | 网格生成、贪婪合并、区块流式加载、LOD 全自写 |
| 做成软件、配置简单 | 导出即 exe，零依赖 | 需桌面壳或"本地服务 + 浏览器" |

three.js 的真实优势在**网页分发**（一条链接，学员零安装），但那是另一条产品路线，与"做成软件发布"互斥。

### 8.1 明确不做

- **不引入 cordis / Node / DSH 作为宿主**
- **不引入物理引擎**。工厂沙盒的底座是离散 tick 模拟 + 确定性回放，不是刚体物理
- **不重蹈 Tauri 的坑**。提交 `5f5d89a` 记录过 Tauri 的 windres 在带空格路径上崩溃，项目路径 `D:\rl course\` 的空格仍在。若将来需要桌面壳，优先 Electron 或先改路径
- **v1 不做通用插件加载器**。三级内核沿用现有 provider 机制；本地小模型作为一个新增 provider 接入，不走插件框架。通用插件化延后到有第二个真实用例时再说

### 8.2 呈现层组成

**主屏 = 体素世界。** 现有五屏的处置：

| 原屏幕 | 新形态 |
|---|---|
| Play / Lab | 融入世界：机器即入口，点开是面板 |
| Tour | 保留为观摹入口（进入世界时的一次演示） |
| Graph | 降级为世界内面板（可切换的 3D 知识星图） |
| Solo | 降级为世界内面板（修坏掉配置的任务界面） |

即：**一个世界 + 若干 overlay 面板**，不再是五个并列整屏。

### 8.3 运行时与 v1 边界

- 学员自己的电脑，Windows only（v1），做成软件发布
- **v1 沿用现有三级内核**（演示确定性离线 / 本地 Ollama / 云 Key），云 Key 由课程组织者在演示机上配置
- **平台侧密钥服务与算力卡 token 发放属 v2**，其前提是账号与计费，而 §1 已把这两项排除出 v1。v1 不实现它，但世界层的 `cost_budget` 计量口径要预留
- **v1 的学员代码按"可信本地代码"对待，不做隔离**。sidecar 只负责 stdio 子进程的启动、健康检查、超时与回收，不负责沙箱。代码隔离属公开产品阶段

### 8.4 MCP 的落位

- **MCP 客户端放在 sidecar（Python 侧）**，Godot 不碰 MCP
- stdio 子进程生命周期由 sidecar 管理（启动、健康检查、超时、回收）
- 工具调用失败与重试映射到现有 verifier 与 Designed Failure 判定，不新造一套错误模型
- v1 只做 stdio，不做 streamable-http

## 10. 实施顺序

**按里程碑拆成多份 plan，不做一个大 plan。** 每个里程碑可独立验收。
