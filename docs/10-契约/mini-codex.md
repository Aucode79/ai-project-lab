# mini codex · 组件与可视化设计

> 2026-09-13 · 设计文档。本文定"我们自带的那个 agent 由哪些组件构成、每个组件在世界里长什么样、怎么看出它跑到哪了"。
> 上游：[`specs/2026-09-13-sandbox-as-studio-design.md`](specs/2026-09-13-sandbox-as-studio-design.md)、[`方块体系.md`](方块体系.md)。

## 为什么是它，而不是另一个子系统

mini codex 有两个身份，恰好都是已有的东西：

1. **它是原 spec §4「观摹」阶段的那只手**——LLM 自己把世界配好并跑完，学员单步回看。本文把这只手具体化成组件。
2. **它的组件就是 U10 四集的教学对象**：E49 profile、E50 记忆机制、E51 工具使用、E52 多智能体。所以设计它等于设计 demo 的内容，不是另起一套。

它同时是**接管阶段的交还对象**：学员从看它做，到改它的参数，到把它关掉自己做。第三个身份是"可以替人操作"——**全可代，但代做时慢速可视**。

## 一、组件清单

组件分三类：**行为件**（对外动作）、**内部件**（模型侧）、**环境件**（世界侧的物）。内部件也做成可见方块，因为它们正是"大模型基础概念"那几章要讲的东西。

| # | 组件 | 类 | 干什么 | 世界里的形态 | 对齐集号 |
|---|---|---|---|---|---|
| 1 | 任务牌 Task | 行为 | 接住学员给的活 | 插在工位的一块牌 | E49 |
| 2 | 角色铭牌 Profile | 行为 | 它是谁、语气、权限边界 | 任务牌背面的一张铭牌 | E49 |
| 3 | 计划板 Planner | 行为 | 把活拆成有序步骤 | 排程板，当前步骤有指针 | E49 |
| 4 | **上下文容器 Context** | 内部 | 把该读的读进来，按窗口预算裁剪 | 带容量刻度的容器，装入的文件码成一摞 | E50、E07、E08 |
| 5 | **思考机 Model** | 内部 | 一次模型调用：提示词进，token 流出 | 一台机器，一侧进纸条、一侧吐 token 方块 | E08、E40、E43 |
| 6 | **记忆柜 Memory** | 内部 | 跨轮保留的笔记 | 抽屉柜，读写时开合 | E50 |
| 7 | 工具带 Tools | 行为 | 读 / 写 / 跑 / 搜 四类工具 | 墙上四把工具，被选中那把发光 | E51 |
| 8 | **文件柜 Files** | 环境 | 世界里的文件系统 | 一排格子，每格一个文件，挂三态灯 | E51 |
| 9 | 执行器 Runner | 行为 | 真跑代码与命令 | 带观测窗的机器，输出在窗里流动 | E51、E60 |
| 10 | 校验门 Verifier | 行为 | 跑测试与断言 | 质检门，通过或拒绝分岔 | E51、E60 |
| 11 | 旁路 Recovery | 行为 | 失败走岔路重试 | 旁路管道 + 重试计数器 | E51 |
| 12 | 回廊 Loop | 行为 | 想→做→看，步数与循环上限 | 带环回廊 + 计数器 | E49 |
| 13 | **机械臂（末端）Arm** | 行为 | **一切修改**的物理载体：抓方块、放进或替换文件柜的格子、拧旋钮 | 接在 mini codex 末端的工具头 | E51、E52 |
| 14 | **扫描器（末端）Scanner** | 行为 | **一切读取**的物理载体：扫过文件柜的格子，命中内容进入上下文 | 同末端的另一只工具头，与机械臂可换 | E50、E51 |

**不设预算表**（用户裁决）：token / ops / 时间不做成刻度表组件。用量仍然记进步记录（诊断与 agent 评分要用），但**不在世界里显示**——激励交给 agent 的多维度评分（见 §四），不再靠"看着额度剩多少"驱动。

**与关卡的关系**：demo 是一条五关的线性关卡链，终点就是这十四件齐备的一台 codex。分组与各自配的视频见 spec §9.1.1（L1 身份 → L2 手脚 → L3 记性 → L4 判断 → L5 跑完与兜错）。

**与方块体系的关系**：这十四件**不是新的方块类型**，而是家族一那一种方块（代码结构方块）按流程拓扑拼出的**预设装配**，外加家族二的展示方块（文件柜、上下文容器的刻度）。所以方块类型总数不变，仍是 **12 种**。

## 二、三个指示器

三个要求各自落在不同的组件上，而且共用同一份数据源——步记录（spec §6）。

### 2.1 跑到它了

每个组件有三态：**待命 / 正在 / 完成**（失败时进第四态"出错"）。状态由步记录的 `actor` 与 `phase` 驱动，**不另做状态机**。相机跟着 codex 本体走，它走到哪台组件、那台就亮——**"跑到它了"由世界本身表达，不另设步骤带**（用户裁决：步骤带与视频功能重复）。

组件上还要带两个读数：**当前步号**与**本组件累计步数**。跑完一遍后，十四块方块本身就是一张"刚才发生了什么"的图。

### 2.2 可读取的文件

文件柜的每一格挂三态灯：

| 灯 | 含义 | 依据 |
|---|---|---|
| 亮 | 可读 | 作用域声明里有读权限 |
| 亮且门开 | 可写 | 作用域声明里有写权限 |
| 上锁 | 禁读 | 不在作用域内 |

作用域来自世界初始化的声明（对应原 spec 的 `permission` 硬约束）。这样"agent 能读哪些文件"不写在文档里，看一眼柜子就知道。执行器与校验门各自也有作用域灯，因为它们读的文件范围与 agent 不同。

**灯只是许可，动作要由工具头执行**：可读的格子只有被扫描器扫到才算真读了；可写的格子只有被机械臂碰过才算真写了。上锁的格子扫过去没有反应，机械臂伸过去会被挡回。

### 2.3 两只工具头：写走机械臂，读走扫描器

**规则一句话：一切修改走机械臂，一切读取走扫描器。** codex 本体在工位之间移动，末端挂一只工具头，可切换。

| 头 | 负责 | 动作 | 留下的痕迹 |
|---|---|---|---|
| **机械臂** | 一切修改 | 从工作台抓一块方块，走到柜格放入或替换；拧旋钮 | **落点与替换**——看得出写了哪里、改的是哪一格 |
| **扫描器** | 一切读取 | 扫过柜格，命中内容进入上下文容器 | **扫描痕迹**——扫过的格子留下淡痕，看得出读了哪些 |

两者的痕迹性质不同，正好对上学员的两个问题：**读不留物、写留物**。

| 工具 | 载体 |
|---|---|
| `fs.read`、`fs.list`、`world.read`、`world.inspect`、`world.snapshot`、`sim.snapshot` | 扫描器 |
| `fs.write`、`world.place`、`world.connect`、`world.set_param` | 机械臂 |
| `run.python`、`run.tests` | 执行器（它产生的文件写回时，仍由机械臂交付） |

**改与新增要能区分**：机械臂放入新方块是"新增"，先取旧再放新是"改"，两者用颜色区分，并各留一格高度的落点标记。

两只工具头都是**装饰实体**（spec §7.1），走烘焙轨道，所以看起来是物理动作。轨迹（淡出的光带）保留一段时间，让学员回看它去过哪些格子。

**代做时慢速可视**：代操作不是后台跑完给结果。工具头按慢速走，每一步**停留**（默认 0.6 秒），学员随时可以按停、接管、回退。这条把"替人操作"和"看每一步"同时保住了。

## 三、MCP：自带的 agent 就是另一个客户端

架构上只有一句话：**mini codex 通过 MCP 接入世界，与学员用的是同一套工具面**。所以它的每一次操作都会落进同一份步记录、走同一套可视化。这是"可以替人操作但保留可视化"能成立的原因——不给它开后门，让它走学员走的那条路。

工具分三组（在 spec §7.2 的骨架上加文件与执行两组）：

| 组 | 工具 |
|---|---|
| 世界 | `world.place` / `world.connect` / `world.set_param` / `world.run` / `world.inspect` / `world.snapshot` |
| 可观测性 | `world.read` / `world.trace` / `world.watch` / `world.step` / `world.diff` / `world.export_netlist` |
| 文件与执行 | `fs.read` / `fs.write` / `fs.list` / `run.python` / `run.tests` |
| 制作（不暴露给学员，也不暴露给 codex） | `studio.bake` / `studio.capture` / `studio.compose` |

**学员的可搬运产出物**仍然是他自己写的 MCP 工具定义与校验器；`world.*` / `fs.*` / `run.*` 是平台侧接口。

## 四、代操作的分寸与交还

| 阶段 | 学员做什么 | codex 做什么 | 对齐大纲 |
|---|---|---|---|
| 观摹 | 看，单步回看每一步 | 全跑一遍，慢速可视 | E49–E52 的默认播放 |
| 接管 | 改一个参数、看结果变化、随时接管 | 从接管点继续，或退到一旁 | E51 参数与校验 |
| 手写 | 从零配置并导出 Python | 关掉，或只做校验与提示 | §7 的可搬运红线 |

**代操作边界**：凡有可判定 `observe` / `fail` 的任务都可代做，但（a）代做全程慢速可视，（b）学员随时可接管，（c）代做的运行标 `kind: production` 或 `explore`，**不参与判定**——判定必须由学员自己的 `judged` 运行产生。这条防止"让 agent 做完就算过关"。

### 4.1 激励：agent 的多维度评分（替代星星与排行榜）

用户裁决：不设预算表、不做星星与排行榜，激励交给 **agent 给多维度评价**。

| 项 | 口径 |
|---|---|
| 谁评 | codex 自己——它就是世界里那个 agent，拿这次的步记录与任务目标比对 |
| 评什么维度（草案，待定） | 正确性（目标达成没有）、结构（流程拆得清不清）、效率（步数与改动次数）、鲁棒性（边界情况处理没有）、可读性（别人看得懂吗） |
| 怎么给 | 给**诊断语句**，不是分数排名。例如"你在第 7 步把校验放在解析之前，所以字段缺失时先崩了" |
| 不评什么 | 不评"聪明"，不给总分行星，不与他人比较 |
| 依据 | 《编程农场》玩家原话——用 AI 帮自己写代码"像在射击游戏里开自瞄，没有挑战，也没有乐趣"。所以评价必须落在**诊断**上：告诉学员下一步改哪里，而不是给一个好坏 |

评分结果落进步记录（作为一次 `task` 运行的产物），可用 `world.diff` 对比两版。

## 五、助学文档写什么

不写成 API 手册。按**三层用法**组织，每层都挂集号与沙盒任务：

| 层 | 回答的问题 | 内容 |
|---|---|---|
| 看它做 | 它现在在干什么、读了哪些文件、为什么这么选 | 十四件组件逐个讲；每件配"什么时候会亮、亮了意味着什么"；配相机跟随的读法 |
| 让它替你做 | 怎么下任务、怎么验收、怎么叫停 | 任务牌的写法；作用域怎么给；验收看哪三个指示器；叫停与回退怎么操作 |
| 你自己做 | 怎么把它拆掉接管 | 组件到代码的对应（每个组件导出成哪段 Python）；先关哪件、后关哪件；判定必须自己跑 |

**文档自身也是世界里的东西**：一块石板（家族二"文本"方块），摆在工位旁边，可以翻开，也可以投影到播放器方块上。这样"查文档"不是一个跳出世界的动作。

## 七、待定

1. **慢速的具体档位**：默认 0.6 秒/步，是否给 0.2× / 0.5× / 1× 三档
2. **工具头轨迹的留痕**：扫描痕迹与机械臂落点各留多久、是否随相机跟随联动回放
3. **codex 的记忆柜与学员的记忆柜是不是同一个**（E50 的教学点在于"记忆是显式的"，两个柜子会更清楚，但会多一件组件）
4. **多智能体（E52）怎么呈现**：多台 codex 各带一副工具头，还是共享一副
5. **工具头切换要不要花时间**：换头本身是否算一步（算的话，学员能看出"它在读还是写"，但要占一步预算）
6. **codex 的模型来自哪里**：沿用原 spec §8.3 的三级内核（离线演示 / 本地 Ollama / 云 Key），demo 用哪一级
