# 方块体系 · 概念怎么变成可视化方块

> 2026-09-13 · 设计文档。本文定"用什么方块画"，是 [`specs/2026-09-13-sandbox-as-studio-design.md`](specs/2026-09-13-sandbox-as-studio-design.md) 的实现前置。

## 为什么需要这份东西

63 集大纲的「画面」栏是**逐集独立写**的。把 E01–E63 的画面对象全抽出来，共 **267 条，其中跨集重复的只有 3 条**（进度条 2 次、三格并排 2 次、准确率曲线 2 次）。所以方块体系不可能从这些画面里"归纳"出来——只能反过来：**先给一套有限的方块词汇，再把 63 集重写进这套词汇**。这意味着大纲 §3 的「画面」栏要整体重写一遍，这是本设计的直接工作量。

## 世界度量体系 · 以方块为基准

> 2026-09-14 增补，同日由「标准方块 · 基本量」扩写为分层口径（用户第二轮需求："所有组件、所有物理实体都以标准方块为基准"）；同日再经渲染预览反馈二次裁决「块状化 v2」——可见件全部入格、豁免层收缩（沿革见下）。唯一尺寸来源：`game/scripts/asset_lib/asset_node.gd` 的 `STANDARD_CUBE_SIZE` 常量。裁决记录见 [`../30-决策/2026-09-14-世界度量体系以方块为基准.md`](../30-决策/2026-09-14-世界度量体系以方块为基准.md)（v2 见其「块状化 v2（同日二次裁决）」节）。

### 基准单位

**定义**：标准方块是**正立方体**，边长 **0.5 m**，形状大小**固定**、不可调。代码里的唯一来源是资产库基座常量 `STANDARD_CUBE_SIZE := 0.5`（`game/scripts/asset_lib/asset_node.gd`）；token 方块没有 `cube_size` 这类可调参数，任何地方不得自定尺寸。

两个量纲都从它派生：

| 量 | 大小 | 说明 |
|---|---|---|
| 1 标准方块 U | 0.5 m | 基本单位，`STANDARD_CUBE_SIZE` |
| 1 世界格 = 1 体素 | 1 m = 2U | 地面体素天然是方块的两倍，整数倍合规 |

**语义**：**1 方块 = 1 个 token/样本**——它是这套世界的**基本量**（基本单位）。尺子要量得准，刻度就得恒定：方块尺寸恒定，"一摞几块""传送带过了几块""计数器跳了几格"数的才是同一种东西，世界里的视觉度量才成立。

**适用范围**：一切 token 方块——资产库 `base_block`（通用方块）、`mach_stacker`（堆叠架码放的方块），以及关卡里的散块（L1 LooseBlock）、工作台待抓块（L2 SpareBlock）等，一律 0.5 m 标准方块。

### 分层规则：谁守格、谁豁免

用户口径（2026-09-14 第二轮）：**所有组件、所有物理实体都以标准方块为基准——包括地面**。落到三层：

| 层 | 对象 | 约束 |
|---|---|---|
| a · 主轮廓尺寸 | 资产 bounding、场景大件外框、物理碰撞体、生成台基座 | 必须 n×0.5 |
| b · 摆位 / 部件中心 | 一切实体摆位、部件装配中心 | 必须 n×0.25（半块网格），整格优先；贴面件半嵌（见下） |
| c · 豁免不计量 | 仅不可见功能面、非几何参数、bench（v2 收缩后） | 不进格子审计 |

- **a 层**：孩子一眼能看出"占了几个方块"的量，必须 n×0.5。资产 bounding、场景大件（机械本体、平台、任务牌架）外框、物理碰撞体、生成台基座都在此列。
- **b 层**：摆位与部件中心必须 n×0.25，即半块网格。**整格优先**——0.25 是"落地中心 / 贴面"这类半块派生的合法值，不是放宽：半块仍是方块度量。
- **半嵌（v2）**：厚 0.25 的贴面件**中心直接落在支撑面的格线上**——半截嵌进支撑体、半截露出。这化解了"贴面件中心必偏移"的矛盾：若浮贴在表面上方，中心 = 表面 + 0.125，永远不在 n×0.25 格点上；半嵌让中心回到格线，露出的半边仍是孩子看得见的 0.25 贴面。
- **圆件方化（v2）**：圆形轮改**方轮**——圆无格可对，方轮四边落格，滚动起落本身就在格上；五关小车轮全部方化。
- **端口吸附（v2）**：端口位置**吸附半块格**（照 b 层受约束），端口标记 `PORT_MARK_SIZE` 由 0.1 升到 0.25——标记本身成为半块见方的可见件，不再豁免。
- **c 层**（豁免不计量，v2 收缩后仅三类）：
  - **不可见功能面**：碰撞检测面、透明拾取体——孩子看不见、不参与"数格子"；
  - **非几何参数**：Label3D 文字、粒子、头灯等纯视觉物，视距、灵敏度、长按阈值等相机与交互手感量——不是几何，与占格无关；
  - **bench 基准场景**（`game/bench/`）：历史测量复现环境，`测量结果.md` 的数字依赖原尺寸复现，不改。

**口径沿革**：本节初版把"非 token 部件（任务牌、铭牌、机械本体、台面等）"整体豁免；第二轮起该豁免废除——它们的主轮廓照 a 层受约束，只有 c 层清单豁免。同日渲染预览反馈（"还有一些小组件不是按方格去呈现的"）后二次裁决「块状化 v2」：c 层里的**工艺件、端口、圆轮豁免全部废除**（原"厚 < 0.25 保原值""端口锚表面 + 伸出量""圆无格可对"均为 v1 口径，2026-09-14 同日经渲染预览反馈后废除）——可见件全部 n×0.25 入格，c 层收缩为上列三类；`base_block` 底座裙边与 `base_label` 0.04 装饰包边两处无法落格的豁免件直接删件。v2 裁决全文见 [`../30-决策/2026-09-14-世界度量体系以方块为基准.md`](../30-决策/2026-09-14-世界度量体系以方块为基准.md)「块状化 v2（同日二次裁决）」节。

**外延落格（2026-09-17 三修，现行口径）**：「块状化 v2」约束的是部件**中心与尺寸**落 0.25 格；用户对
"(x,y,z) 唯一确定"取**最严读法**后，教学资产升格为**部件盒外延六面全部落 0.25 m 格点**（"占满整格"）——
等价条件：同一资产所有部件面同相位 mod 0.25，且可见包络每轴总宽为 0.5 的整数倍；**中心允许 0.125 m

### 为什么分层，而不是"一切 n×0.5"

严格"一切 n×0.5"在三处无解：

1. **薄板**：厚度 0.06~0.16，强制吸附到 0.25 的倍数，就近会吸到 0——厚度为零，板直接灭失；
2. **端口**：位置 = 表面 + 伸出量，两个量都不是格点倍数；强制落格，端口要么悬在空中要么嵌进壳体；
3. **高度链**：叠放高度 = 底座 + 板厚 + …，厚度参与加法，逼工艺件守格就是逼薄板灭失，不逼则链尾全歪。

所以分层：**孩子看得见的占格量（主轮廓、摆位、可数的方块）全部以方块为单位，看不见、不参与"数格子"的工艺细节不逼死**。0.25 之所以合法，是因为它是半块（0.5 块），仍是方块度量，不引入第三种单位。

**块状化 v2 之后**：上面三处"无解"在同日二次裁决里全部有了答案——薄板不再保原厚度而是一律升到 0.25（最低厚 0.25、半嵌落格，板不会灭失）；端口吸附半块格；高度链全部由 0.25 的倍数相加，链尾不歪。分层的"为什么"由此改写：**看得见的全部入格，豁免只留给看不见的**（不可见功能面、非几何参数）与不可改的（bench）。

### 教学语义

- **孩子数格子即知数量**：机器平台 13×13 格，用方块一数就是 26×26 块——格与块只差一个固定的 2 倍；
- **token 方块 1 块 = 1 个数据单位**：数块就是数数据，堆叠、传送、计数的读数都成立；
- **组件尺寸报方块数**：说"宽 4 块、高 2 块"，不说"宽 2 m"——米是引擎内部单位，对孩子不出现。

### 待裁决清单（开放问题）

1. **端口是否对齐半块格**：**已裁决（2026-09-14 v2：做）**——端口位置吸附半块格，端口标记 0.1 → 0.25（见分层规则「端口吸附」）。
2. **工艺件是否全面"块状化"**：**已裁决（2026-09-14 v2：做）**——可见件全部 n×0.25、中心落 n×0.25 格、半嵌贴面；豁免清单随之收缩（见分层规则 c 层）。
3. **圆形轮是否方轮化**：**已裁决（2026-09-14 v2：做）**——圆件方化，五关小车轮改方轮。
4. **体素分辨率是否从 1 m 提到 0.5 m**：**仍开放**——1 体素 = 1 方块的严格 Minecraft 模型；数据量与坐标重构成本大，当前以"1 体素 = 2U"声明替代。

## 一、两个家族

方块的第一个分界不是"难易"，是**能不能被学员写代码算出来**。

| | 家族一 · 代码结构方块 | 家族二 · 非代码功能方块 |
|---|---|---|
| 承载 | 程序的构造：值、函数、参数、调用、循环、校验、接口 | 一切非代码内容：图表、表格、对话、图像、模型输出、文本 |
| 可操作 | 能拼、能连、能改参数 | 只读或展示 |
| 能导出 Python | **必须能** | 不能，本来就不是代码 |
| 定形规则 | 形状 = **流程拓扑** | 形状 = **内容类型** |

**分界规则（唯一判据）**：能被学员写代码算出来的归家族一，只能读不能算的归家族二。

边界案例按这条判据处理：

| 对象 | 归属 | 理由 |
|---|---|---|
| 概率分布 | 两边都有 | softmax 的输出是值（家族一）；论文里那张分布图是读图（家族二） |
| 排序 | 两边都有 | 自己写排序是循环加数据结构（家族一）；NDCG 那张排序图是读图（家族二） |
| 实验设置表 | 家族二 | 只能读，不写代码 |
| 张量、矩阵、向量 | 家族一 | 是可计算的值，只是**显示样式**不同（格子 / 色条 / 柱状） |
| 进度条、集号标记 | 都不属于 | 属版式，由图层固定承担，不做成方块 |

## 二、家族一的定形：形状 = 流程拓扑

**家族一只做一种方块**（代码结构方块）。分类统计显示，这套课里属于代码结构的画面对象只有 28 条、分布在 16 集，且集中在五件事上：定义数据结构、声明接口签名、传参、断言校验、报错——它们本来就在同一条 Python 产物链上。把它们拆成 5 种方块，会让每集都要多装配几个零件，不划算。所以：**类型是 1 种，形状是 5 种拓扑变体**。

学员看形状就知道这条流水长什么样，而且**形状错了能被一眼看出来**——该带环的流程画成直线，就是少了回环。这是"每个流程一个独有形"做不到的：那种形状只是吉祥物，不携带信息。

| 拓扑 | 形状 | 一看就懂的意思 | 落在大纲哪里 |
|---|---|---|---|
| 直线型 | 一条直通道 | 一路走到底 | 数据流水线、解码一步、评测流程 |
| 分岔型 | Y 形岔口 | 这里要选一条 | 条件分支、schema 校验的通过/拒绝、采样策略选择 |
| 带环型 | 回环 | 会转回来 | 训练循环、epoch、Agent 的 think→act→observe |
| 扇出型 | 一发多路 | 并发或分裂 | 多工具并行调用、多智能体、batch 拆分 |
| 汇聚型 | 多路归一 | 合成一路 | 池化、RAG 的 top-k 取回、评测汇总 |

## 三、家族一的三级粒度

粒度直接从粗到细，与教学法的三阶段递进一一对应（原 spec §4）。

| 级别 | 单位 | 学员做什么 | 阶段 | 需要编程基础 |
|---|---|---|---|---|
| 一级 | 一个**典型工程流程**（整段，拓扑定形） | 看整条跑完，认形状 | 观摹 | 不需要 |
| 二级 | 流程拆开露出的**旋钮** | 改一个参数，看结果变化 | 接管 | 不需要 |
| 三级 | **代码结构方块**（函数 / 调用 / 循环 / 校验 / 接口 / 错误处理……） | 从零拼装，导出 Python | 手写 | 需要 |

一级是入口：**孩子从大段流程开始，无需编程基础**。三级是终点：拼装即写代码，导出物能跑。

## 四、入门流程方块（一级）

一级的"整段流程"**不是新的方块类型，而是出厂预设装配**——用家族一那一种方块按拓扑预先拼好的一条流程，学员一进来就看到完整的它，不需要编程基础。

按典型工程流程切，不按章切，也不按单元切——章是知识分类，不是流程。

| 预设流程 | 拓扑 | 现实对应 | 主要挂靠章节 |
|---|---|---|---|
| 数据流水线 | 直线型 | 采集→清洗→变换→划分 | 一、四 |
| 训练循环 | 带环型 | 前向→损失→反向→更新，按 epoch 转 | 四 |
| 微调流程 | 带环型 + 分岔 | 指令数据→LoRA/全参→多阶段 | 五 |
| 推理与解码 | 直线型 + 分岔 | 前缀→采样策略→输出 | 七 |
| RAG 检索 | 扇出 + 汇聚 + 直线 | 查询→检索多路→排序取回→拼进上下文 | 八 |
| 工具调用 | 分岔型 | 生成调用→解析→schema 校验→通过或拒绝 | 十 |
| Agent 循环 | 带环型 + 扇出 | 想→并行调工具→观察→再想 | 十 |
| 评测流程 | 直线型 + 汇聚 | 划分→跑测→算指标→汇总 | 十一 |

**但要按数据收敛**：家族一在整套课里只覆盖 16 集（E06、E07、E11、E13、E14、E20、E26、E29、E37、E41、E42、E49、E51、E53、E60、E62），另外 47 集是纯展示画面。所以这八个预设不必一次全做，**先做落在那 16 集里的**（工具调用、Agent 循环、训练循环、推理与解码、评测流程优先，它们对应 E49/E51/E20/E37/E53 等）。

## 五、家族二的定形：形状 = 内容类型

家族二共 **11 种**（下面这张表就是权威清单）：

| # | 类型 | id 前缀 | 形状 | 承载什么 |
|---|---|---|---|---|
| 1 | 图表 | `chart_` | 透明展柜 | 分布、曲线、柱状、条形比较、排名图 |
| 2 | 表格 | `table_` | 格子桁架 | 实验设置表、指标对照、超参表 |
| 3 | 流程/拓扑图 | `flow_` | 平铺管路 | **展示用**的流程图（可操作版属家族一） |
| 4 | 文本/条目 | `text_` | 石板 | 定义、结论、要点 |
| 5 | 概念示意图 | `concept_` | 悬浮拼件 | 嵌套圆环、四象限、结构类比 |
| 6 | 算式/推导 | `formula_` | 阶梯式刻板 | 公式推导、逐步演算、数值代入 |
| 7 | 时间轴/进度 | `timeline_` | 直尺带 | 时间轴、阶段划分、进度 |
| 8 | 对话 | `dialogue_` | 喇叭口 | 提示词、模型回答、多轮交互 |
| 9 | 图像/输出 | `output_` | 画框 | 生成的图、检测结果、原始返回、JSON |
| 10 | 播放器 | `player_` | 幕布 | 微课成片本身 |
| 11 | 兜底展示 | `fallback_` | 通用展台 | 放不进上面十类的（逐条登记，见 §七） |

**不计入方块类型的两类**：`版式/分区`（集号、进度条、字幕条这些固定版式，由图层承担，不做方块）与 `其他`（归入兜底展示）。

### 5.1 播放器方块：视频与动手合到一处

**播放器方块是整个世界交付面**：学员在沙盒里走到幕布前看这一集的成片，看完当场在同一个世界里跟着做一遍。这一步把两件事合一了——

- 视频不再是另一个软件里的东西（"看视频"和"做任务"本来是两个 App，现在是一个）
- 任务的落点不再需要逐集指定：**凡是这一集里演过的流程，学员就在原地复现它**；能不能复现，取决于这一集的方块是否可操作（家族一），不能操作的（定义与史论、模考讲评、论文阅读）看完即止

它也让"集号"成了世界里的地址：集元数据（`episodes/e51.json`）同时服务课程页、播放器、任务与进度统计，仍是同一个事实源。

**播放器不是新的方块类型**，它是家族二"幕布"这一种，与其他展示方块并列；差别只在于它播放的是成片，且可挂任务。

**幕布有两种用途，分成两块**：播放成片（**播放器**）与答疑对话（**求助屏**）。用户裁决"做不同的事情本来就可以分开"——看片是被动接收、问答是主动交互，各自一块。求助不放在 HUD 上，而是世界里一个走得过去的东西；空间成本本身就是摩擦，能防止孩子反射式地问而不先想。

## 六、与导出红线的关系

家族一**必须能导出 Python**，这条把"可搬运性"从口号变成可测的判据：拼装动作本身就是生成代码骨架，导出物必须能跑（由 sidecar 执行，原 spec §8.3）。也就是说，**学员在沙盒里拼的东西，和他要带进考场的东西，是同一份文件**。

家族二不导出，它承担另一个明确考点：大纲 §5 写明论文阅读不写代码，但要会读三样东西——实验设置表、条形图数值比较、阈值判定规则，材料题 3 就是这三样，共 12 分。

### 6.1 这是一门语言，抽象层级在 Scratch 之上

我们没设计新语言，但方块体系事实上是一门语言：有词汇（12 种方块）、有语法（端口连接 + 参数）、有语义（编译成 Python）。差别在抽象层级：

| 系统 | 积木与代码的关系 | 最近的亲 |
|---|---|---|
| Scratch / Blockly / MakeCode / App Inventor | **一个积木 = 一行代码**（1:1） | — |
| **我们** | **一个方块 = 一个结构**（函数、调用、循环、校验、接口……）；一级预设装配 = **一整段流程**，也就是折叠起来的子网络 | Simulink 的 Subsystem、Unreal Blueprints 的 Collapse to Function、Houdini 的 Subnet、Max/MSP 的 abstraction |

所以对标的不是 Scratch，是**"节点即算子、子网络可折叠"**那一类工具。

### 6.2 编译器契约

> **2026-09-22 新 Agent 系统补充（已实施）**：增加共享模块定义、接口调用和递归；方块为唯一编辑入口，控制流与数据流驱动生成 Python。新格式为 module/1，Godot 与后端共用 Python 编译器；具名端口在模块图编辑，三维整机映射根程序与运行事件。详见[验收](../20-验收/2026-09-22-可执行Agent沙盒.md)、[实施方案](../00-入口/2026-09-22-可执行Agent沙盒实施方案.md)与[决策](../30-决策/2026-09-22-沙盒模块作为可执行代码.md)。以下单图编译与折叠不变量仍描述既有实现；§6.3 的三级是查看示例，不再限制新系统层数；§6.4 的手改代码与重排路径不纳入新系统。

编译器是正式交付物（进原 spec §9 的新增清单）。

| 项 | 口径 |
|---|---|
| **输入** | **连接图 + 参数 + 装配层次**：实体与端口、端口之间的连接、每个实体的参数值、哪些实体被折叠成一个预设装配 |
| **不读** | **位置与朝向**。同一份逻辑换个摆法必须编译出同一份代码 |
| **输出** | 可搬运的**普通 Python**：MCP 工具定义、参数校验、错误恢复、控制循环（原 spec §7 的红线）。不是自有 DSL，因为要能直接带进考场 |
| **中间表示** | 连接图 → IR（数据流 + 控制流）→ Python。IR 是编译器内部结构，不暴露给学员 |
| **编译期校验** | 端口类型匹配、必需端口未连接、参数越界、隐式依赖成环、循环必须有显式出口。**在拼装时即时反馈**，不等编译 |
| **运行期校验** | 与编译期分开：物理是否卡住、输入是否坏，属于"程序跑起来之后"的事 |

**"读取物理情况"的准确含义**：读的是**世界的连接与参数状态**，不是几何。物理影响的是执行（会不会卡住、时间先后），不影响编译结果。这条要写死——否则"同一份逻辑两种摆法、两种代码"，教学会崩。

### 6.3 折叠与展开是头等操作

三级粒度其实就是**折叠 / 展开**：

| 级 | 状态 | 同类的现成操作 |
|---|---|---|
| 一级 | 一段流程**折叠成一个方块** | Blueprints 的 Collapse to Function / Simulink 的 Subsystem / Houdini 的 Subnet |
| 二级 | 展开一层，露出旋钮 | 子系统参数面板 |
| 三级 | 全展开，露出代码结构方块 | 展开成基本节点 |

所以编译器必须把"折叠"当成一等操作：**同一个连接图，折叠层次不同，编译出的代码必须相同**（折叠只改视图，不改语义）。这条是三级粒度能成立的前提，也是"拼装与代码两模式互通"的技术基础。

### 6.4 双向：单向为主，另给一个「重排」

- **拼装 → 代码**：编译器负责，主路径
- **代码 → 拼装**：**不做自动布局**（那是布局合成问题，成本高且容易排得难看）。手改代码后，拼装视图标记为「已脱离」；学员可点「重排」让编译器按代码重摆一版，重排是**有损**的（注释、手写的局部结构会丢），因此只在学员主动要求时做

这样手写代码的人不会被拖回积木视图，积木派也不必碰代码。
